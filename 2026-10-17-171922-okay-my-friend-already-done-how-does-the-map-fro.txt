⏺ Done reading both codebases. Here's the plan.

  What exists now

  Your app (prototype/): static HTML/JS with no backend. It's the Cork Harbour
  sim on a synthetic seabed: WASD helm, Port/Bridge view, keel view, advisory,
  AGROUND banner. ukc.js (prototype/ukc.js) is tested.

  Friend's app (ground-zero/): Python Streamlit with two pages, UKC what-if and
  Sail planning. It uses real SHOM HOMONIM bathymetry on a grid of 5922×4813
  cells (float32, 114 MB, memory-mapped). Routing runs Dijkstra over that grid,
  then simplifies the path and scores confidence bands. The maps are Leaflet
  templates.

  The good news: their ukc.py and routing.py don't depend on Streamlit at all.
  Only ukc_page.py and route_page.py touch Streamlit, so the maths moves over
  cleanly.

  Architecture (recommended)

  Small Python API plus your static frontend. No Streamlit.

  - server/: copy in their ukc.py, routing.py and BathyGrid, and add a FastAPI
    app that serves prototype/ and these endpoints:
    - GET /api/ships, GET /api/meta (bounds, categories, bands)
    - GET /api/ukc: the payload code from ukc_page.py, almost line for line
    - POST /api/route: plan_route plus the auto-widen loop moved out of
      route_page.py, plus the corridor depth window for the game. The window is
      at most 400k cells, which is about 0.8 MB stored as Int16 decimetres.
    - GET /api/contours?bbox=: clipped server-side. Right now the whole 42 MB
      contours.json gets pushed on every Streamlit rerun.
  - Frontend: three pages sharing one nav bar, with no SPA framework:
    - port.html: your current index.html, unchanged
    - ukc.html: their map_template.html JS, with the __DATA__ injection replaced
      by a fetch, and HTML controls replacing the Streamlit sidebar
    - sail.html: their route_template.html JS, plus the game
  - Bathymetry data stays out of git. Point DATA_DIR at ground-zero/data.

  Why not embed Streamlit in an iframe? Streamlit reruns the whole script on
  every input change, so it can't run a game loop updating every frame. It would
  also mean two stacks and two looks.

  Why not do everything in JS? We'd have to rewrite Dijkstra and the distance
  transform, and you can't ship a 114 MB grid to the browser.

  Gamify: "Google Maps says 15 min, it takes 30"

  Show three ETAs:
  1. Plan says: route length divided by planned speed. This is what their app
     shows now: the naive number.
  2. Water says: along the route, speed is capped by maxSafeSpeed() from your
     ukc.js (prototype/ukc.js). Shallow stretches force a slowdown because of
     squat, so the ETA gets longer. That's the "real traffic" number, computed
     with no player needed.
  3. You did: the player's own run.

  Core mechanic: the player picks a path and a speed for each leg. Faster means
  more squat, which means a smaller UKC. That's the real trade-off behind
  groundings, so the game teaches the pitch.

  - Mode A, draw route (MVP): click waypoints inside the corridor and set a
    speed per leg. The browser checks it instantly against the corridor grid
    using ukc.js. A ghost ship then sails the planner's route at the "Water
    says" pace next to yours. Results: time, minimum UKC, nm sailed in
    caution/critical, any grounding.
  - Mode B, take the helm (stretch): reuse step(), footprint() and the keel view
    from sim.js (prototype/sim.js). The only seam to swap is cellAt() (pixels →
    lon/lat on the corridor grid). Time needs compressing about 300× so a run
    lasts about 90 s.

⏺ Short answer: you don't have to, but for the hackathon I'd build on their
  Streamlit app.

  What actually decides it: the game needs two things from their Python code,
  the planned route and the corridor depth grid. Streamlit has no JSON API, so
  your own page can't fetch that data from it. That leaves two ways to get it
  into the game:

  1. Put the game in their Streamlit app (recommended). Their route_page.py adds
     the depth grid to the data it already sends the map. You write the game in
     plain JS inside route_template.html. Your Cork sim becomes a third "Port
     view" page, shown in an iframe.
     - No new server code, and their two pages already work on real data.
     - The work splits cleanly: they own the Python, you own the template JS, so
       you rarely touch the same files.
     - Downside: changing any sidebar control reloads the map and resets a game
       in progress. You'd also have two visual styles.
  2. Keep your interface as the main app. Write a small FastAPI server (about
     100–150 lines) that wraps their ukc.py and routing.py and returns JSON.
     Your pages call it. Their Streamlit pages get retired.
     - One look, one server, no resets.
     - Costs that server plus rebuilding both of their sidebars in HTML, which
       is a few hours their app already gives you for free.

  Switch to option 2 only if:
  - judges must see one polished app with one style,
  - the reset during play turns out to hurt the demo, or
  - you want the full WASD helm mode with your keel view on real data and it
    gets awkward inside their template.

  The game code itself (route drawing, ghost ship, UKC checks with your ukc())
  is plain JS either way. So if you start with option 1 and move to option 2
  later, you rewrite the data source, not the game.
